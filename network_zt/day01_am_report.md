## ping

### 문제 결과 화면 읽기

- 보냄 · 받음 · 손실 · 평균: 10/10/0/35ms
- 손실 % 는 보낸 수와 받은 수로 어떻게 계산했나요?
  - 답: 10/10

### 문제 구글 DNS 서버에 `ping` 열 번 보내기

- `8.8.8.8` 까지 평균 왕복 시간 · TTL · 받음 · 손실: 35ms/115/10/0

### 문제 이름으로 `ping` 보내기

- `google.com` 의 IP 주소: 142.250.197.238
- 이름만 입력했는데 IP 주소가 나온 이유는 무엇인가요?
  - 답: DNS 서버가 이름에 대응하는 IP 주소를 알려주기 때문

### 문제 두 가지 실패를 구별하기

- 두 실패 문구: 호스트를 찾을 수 없습니다. / 요청 시간이 만료되었습니다.
- 두 실패는 각각 어디에서 멈춘 것인가요?
  - 답: DNS 단계, 이름을 IP로 못바꿔서 패킷에 못보냄. / 전달단계, IP는 알았지만 응답없음

**찾아본 것**

- 2.1 표에서 찾아 쓴 TTL 의 뜻과 라우터를 지날 때 바뀌는 방식: 
  TTL(Time To Live)은 IP 패킷이 네트워크에서 살아 있을 수 있는 횟수로, 패킷이 무한히 떠도는 것을 막는다. 
  라우터를 하나 지날 때마다 1씩 줄고, 0이 되면 그 라우터가 패킷을 버리고 보낸 쪽에 시간 초과(Time Exceeded)를 알려 준다.

**이 교시에 새로 안 것**

- 이 교시에서 새로 알게 된 것: ping 은 IP 로만 보낼 수 있어서 이름을 쓰면 먼저 DNS 가 IP 로 바꿔 준다는 것, 
  그리고 "호스트를 찾을 수 없음"(DNS 단계)과 "요청 시간 만료"(응답 없음 단계)가 서로 다른 실패라는 것을 알게 되었다.

## IP 와 MAC

### 문제 결과 화면 읽기

- 예시 화면의 IPv4 주소 · MAC 주소 · 기본 게이트웨이: 
IPv4 주소: 192.168.100.115
기본 게이트웨이: 192.168.1.1
MAC 주소: D8-BB-C1-40-36-C9

### 문제 내 IP 주소 · 게이트웨이 · MAC 주소 찾기

- 찾은 장치 이름 · 내 IPv4 주소 · 기본 게이트웨이 · MAC 주소(물리적 주소):
장치 이름: Realtek PCIe 2.5GbE Family Controller
IPv4 주소: 192.168.100.115
기본 게이트웨이: 192.168.1.1
MAC 주소: D8-BB-C1-40-36-C9

### 문제 게이트웨이까지 `ping`

- 게이트웨이까지 평균 · 2-2 의 `8.8.8.8` 평균: 0ms (1ms 미만) / 35ms
- 게이트웨이까지가 더 짧은 이유는 무엇인가요?
  - 답: 게이트웨이(공유기)는 같은 내부망 안에 있어서 라우터를 거치지 않고 바로 닿는다. 반면 8.8.8.8 은 인터넷을 지나 멀리 있는 서버라서 거리와 거치는 장비가 많아 시간이 더 걸린다. (TTL 도 게이트웨이는 64 그대로, 8.8.8.8 은 115 로 라우터를 여러 개 지났다.)

### 문제 ARP 캐시 보기 — `arp -a`

- 게이트웨이 줄의 MAC 주소 · 유형: 00-10-f3-a3-fc-96 / 동적
- 🔍 ARP 는 무엇을 알아내려고 쓰나요? 내 결과의 게이트웨이 줄을 예로 들어 설명합니다.
  - 답: 같은 네트워크 안에서는 IP 주소만으로는 패킷을 보낼 수 없고 상대의 MAC 주소가 필요하다. ARP 는 "이 IP 의 MAC 주소가 뭐야?"를 물어서 알아내는 방법이다. 내 결과에서는 게이트웨이 192.168.1.1 의 MAC 주소가 00-10-f3-a3-fc-96 이라는 것을 알아내 저장해 둔 것이고, 유형이 동적인 것은 자동으로 알아낸 값이라 시간이 지나면 지워지고 다시 물어본다는 뜻이다.

### 이 교시에 새로 안 것

- 이 교시에서 새로 알게 된 것: IP 주소와 MAC 주소는 역할이 다르다는 것을 알게 되었다. 같은 네트워크 안에서는 IP 만으로는 보낼 수 없고 ARP 로 상대의 MAC 주소를 알아내야 한다. 내 컴퓨터의 `arp -a` 에서 게이트웨이 192.168.1.1 이 00-10-f3-a3-fc-96 으로 저장된 것을 직접 확인했다. 또 게이트웨이까지는 0ms, 8.8.8.8 까지는 35ms 로 차이가 나는 것을 보고, 같은 내부망 안과 인터넷 너머의 거리가 응답 시간에 영향을 준다는 것을 알게 되었다.

## 포트

### 문제 직접 실행해 보기

- 출력 두 줄: HTTPS / 사전에 없음
- `3389` 는 사전에 없는데도 에러 없이 둘째 줄이 나온 이유는 무엇인가요?
  - 답: `.get()` 은 키가 사전에 없을 때 에러를 내지 않고 두 번째로 준 기본값("사전에 없음")을 돌려주기 때문이다. `ports[3389]` 처럼 `[]` 로 찾으면 KeyError 가 난다.

### 문제 지금의 연결과 그 프로그램 — `netstat -ano`

- 고른 줄의 외부 포트 → 서비스 이름 · PID → 프로그램 이름: 443 → HTTPS / 10268 → Code.exe (VS Code)

### 문제 내 PC 의 LISTENING 포트 찾기

- 4.1 표에 있는 LISTENING 포트 → 서비스 이름: 135 → RPC / 445 → SMB (파일 공유)
- 🔍 LISTENING 과 ESTABLISHED 는 무엇이 다른가요? 4-2 와 4-3 에서 본 줄을 예로 들어 설명합니다.
  - 답: LISTENING 은 서버가 포트를 열어 놓고 연결이 오기를 기다리는 상태이고, ESTABLISHED 는 상대와 연결이 맺어져 실제로 통신 중인 상태이다. 내 PC 의 `0.0.0.0:445` 는 LISTENING 이라 외부 주소가 `0.0.0.0:0` 으로 아직 연결 상대가 없다. 반대로 `192.168.100.115:50088 → 20.200.245.245:443` 은 ESTABLISHED 로, VS Code(PID 10268)가 외부 서버와 HTTPS 로 연결되어 통신 중인 줄이다.

### 문제 증상으로 층 좁히기

- 증상 ① · ② · ③ 에서 의심되는 층: ① 네트워크 계층(3계층) / ② 데이터 링크 계층(2계층) / ③ 전송 계층(4계층)
- 증상마다 그렇게 판단한 근거는 무엇인가요?
  - 답: ① ping 은 IP 주소로 ICMP 패킷을 보내 목적지까지 닿는지 보는 도구라서 IP 와 라우팅을 다루는 네트워크 계층 문제로 본다. (이름이 IP 로 안 바뀌는 경우는 DNS 단계까지 같이 확인한다.) ② MAC 주소와 ARP 는 같은 네트워크 안에서 IP 를 MAC 으로 바꿔 상대 장비를 찾는 일이라 데이터 링크 계층 문제로 본다. ③ 포트 번호와 LISTENING · ESTABLISHED 같은 연결 상태는 TCP · UDP 가 다루므로 전송 계층 문제로 본다.

**찾아본 것**

- 4.1 표에서 찾아 쓴 3389 의 위험과 445 를 이용해 퍼진 랜섬웨어: 3389 는 원격 데스크톱(RDP) 포트로, 인터넷에 열려 있으면 비밀번호 대입 공격으로 PC 를 원격에서 장악당할 위험이 있다. 445 는 SMB(파일 공유) 포트이고, 이 포트의 취약점을 이용해 2017년에 WannaCry 랜섬웨어가 전 세계로 퍼졌다.

**이 교시에 새로 안 것**

- 이 교시에서 새로 알게 된 것: 포트는 한 컴퓨터 안에서 어떤 프로그램(서비스)에게 보낼지 구분하는 번호라는 것을 알게 되었다. `netstat -ano` 로 내 PC 의 LISTENING 포트(135, 445 등)와 ESTABLISHED 연결을 볼 수 있고, PID 로 `tasklist` 를 조회하면 연결을 만든 프로그램(VS Code)까지 찾을 수 있다. 또 445 처럼 열려 있는 포트가 공격 통로가 될 수 있어서 필요 없는 포트는 닫아야 하고, 증상에 따라 ping(3계층), MAC · ARP(2계층), 포트(4계층)로 문제의 층을 좁혀 볼 수 있다는 것도 알게 되었다.
